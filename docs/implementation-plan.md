这是设计推进顺序，不要求按表格逐个建设相互脱离的子系统。进入可运行实现时，需要将已确定的模型组成可验证的最小完整流程；外部生成涉及的 Plugin、Asset、凭证和安全策略不能用占位代码跨过。

第 ⑪ 步列入 SubWorkflow 只表示届时讨论适用范围，不授权引入任意循环或项目下多个独立画布 / 工作流。若后续需求影响现有顶层约束，先说明具体影响并记录决策。

## 下一步：② Workflow 的讨论范围

围绕以下问题逐项形成明确结论，暂不展开节点种类或数据库表：

1. Workflow 承担什么职责，与 Project 和 Canvas 如何分工？
2. Workflow 的逻辑结构由哪些部分组成，哪些属于定义，哪些属于编辑视图或运行数据？
3. 草稿修改、现有 `revision` 与不可变工作流版本如何区分？何时形成运行绑定的版本？
4. Workflow 如何声明输入与输出，如何在边界校验？
5. WorkflowRun 如何绑定版本、接收输入、引用本次 State 与产物？运行修改与草稿修改如何隔离？
6. 一个项目的单一逻辑 Workflow 如何容纳多个版本和多次运行，而不增加多画布层级？

已确定的约束继续适用：运行绑定不可变定义，草稿修改不影响已有运行；定义不携带密钥；contracts 不依赖 React Flow、NestJS、Prisma 或 LangGraph。具体字段、发布动作、状态枚举和运行控制接口仍待本步讨论，本文不预设答案。

## 从设计进入代码

每一步先记录职责、关系、失败边界、已决策项与待决策项，再按当轮明确范围实现。需要代码时按以下顺序推进：

1. 对照现有实现和官方资料核实技术事实，明确当轮会改变的真实行为与验收条件。
2. 在现有应用与包中实现必要契约、适配和业务逻辑；边界稳定且确有复用需求后再拆包，不为概念清单预建框架。
3. 接口、执行语义或数据库发生变化时同步更新文档和必要的行为测试；数据变更遵守 [协作规范](../AGENTS.md)，仅在确有必要时重置本项目开发数据。
4. 执行与改动相关的检查，交付时区分已实现、已验证、未验证与仍待设计的内容。缺少真实模型凭证时明确记录，不用测试适配器代替生产能力。

基础工程启动和检查入口保持现状，见 [开发指南](development.md)。后续每步以当轮新增能力更新架构和实施状态，不把整张路线图一次性作为开发授权。
