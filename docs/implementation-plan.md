# 分步设计与实施方案

本文管理从平台边界到领域生产能力的设计顺序。顶层结论见 [平台核心模型](platform-model.md)，Workflow 层结论见 [Workflow 模型](workflow-model.md)，已实现能力见 [当前架构](architecture.md)。本方案不以设计记录代替功能交付。

## 当前阶段

2026-10-19：已记录 **① 平台是什么** 与 **② Workflow** 的设计边界，已实施 Workflow 基础 Schema、显式组合校验、值契约校验、输出收集、只读版本快照及运行版本一致性检查。具体实现范围见 [Workflow 基础库](architecture.md#workflow-基础库)。下一步为 **③ Node**，继续把已明确且能独立验证的部分同步实施；具体 Node / Edge / DataType、应用接口、持久化及执行调度仍待补齐，其余步骤不视为已确认的详细方案或实施任务。

本文件集中维护当前阶段、下一步与待决策项；已实现能力与目录结构统一见 [当前架构](architecture.md)。推进时直接修订阶段与方案，不追加已被替代的旧计划或逐轮交付流水。文档整理方式见 [开发指南](development.md#文档维护)。

这是设计推进顺序，不要求按表格逐个建设相互脱离的子系统。进入可运行实现时，需要将已确定的模型组成可验证的最小完整流程；外部生成涉及的 Plugin、Asset、凭证和安全策略不能用占位代码跨过。

Workflow 的可组合性与被调用版本固定原则已在 [Workflow 模型](workflow-model.md#workflow-组合与-subworkflow-边界) 确定。第 ⑪ 步继续细化父子运行、批量、并行与生命周期，不授权引入任意循环、递归调用或项目下多个独立画布 / 工作流。若后续需求影响现有顶层约束，先说明具体影响并记录决策。

## 下一步：③ Node 的讨论范围

围绕统一抽象逐项形成结论，不先为每类节点建立一套独立执行系统：

1. LLM、剧本生成、图片生成、Human Review、If、Tool 等节点共享哪些定义、输入输出与配置边界？
2. 节点的类型声明、工作流内实例、执行器与 NodeRun 如何分工？
3. 通用能力与领域节点如何表达差异，而不把漫剧等领域语义写进 Runtime？
4. 节点如何声明能力需求、输入端口和输出键，让 Workflow 输入输出与数据绑定能够校验？
5. 控制节点、人工介入节点及未来 SubWorkflowNode 如何接入统一契约，并保持执行激活与数据传值分离？
6. 哪些内容属于静态定义，哪些只属于执行上下文与运行结果？

已确定的约束继续适用：运行绑定不可变定义，草稿修改不影响已有运行；定义不携带密钥；contracts 不依赖 React Flow、NestJS、Prisma 或 LangGraph。已有 Schema 组合器不能替代具体 Node、Edge、DataType 协议；完整结构、编辑与发布接口、状态转换及存储结构仍需按相关步骤细化。

## 从设计进入代码

每一步记录职责、关系、失败边界、已决策项与待决策项；已经明确且能独立验证的部分随设计同步落到代码，不等待所有步骤设计完成或用户再次要求实施。对仍未确定的部分保留边界，不用占位类型或实现冒充可用功能。实施按以下顺序推进：

1. 对照现有实现和官方资料核实技术事实，明确当轮会改变的真实行为与验收条件。
2. 在现有应用与包中实现必要契约、适配和业务逻辑；边界稳定且确有复用需求后再拆包，不为概念清单预建框架。
3. 接口、执行语义或数据库发生变化时同步更新文档和必要的行为测试；数据变更遵守 [协作规范](../AGENTS.md)，仅在确有必要时重置本项目开发数据。
4. 执行与改动相关的检查，交付时区分已实现、已验证、未验证与仍待设计的内容。缺少真实模型凭证时明确记录，不用测试适配器代替生产能力。

基础工程启动和检查入口保持现状，见 [开发指南](development.md)。后续每步以当轮新增能力更新架构和实施状态，不把整张路线图一次性作为开发授权。
