# 开发参与指南

## 第一遍如何阅读

1. 阅读 contracts，理解工作流定义、运行结果、插件选择与上下文清单。
2. 从前端保存按钮跟到 API 的 workflows 服务，观察 revision 校验和不可变发布版本。
3. 从 runs 启动跟到队列，再到 worker 和 workflow runtime，区分调度与持久化宿主。
4. 跟一次插件调用，确认凭证只在宿主解密、素材转成资产引用。
5. 阅读 context 的 buildContext，再看会话服务如何保存原文、摘要与建议。

无需一次读完全部代码。先选择一条真实操作，把输入和输出对照起来。

## 日常开发

按照 README 初始化环境后，`pnpm dev` 启动应用及共享包构建。修改单包时可以 `pnpm --filter @dramaflow/context test`。共享包通过 dist 暴露，根 Turbo 任务会先构建依赖，避免生产环境直接执行 TypeScript 源码。

`.env` 只在根目录维护；根命令负责加载。直接进入子目录运行服务时，需要自行传递同样环境，不要复制多份秘密文件。

## 修改时的检查

- 只改文档：检查链接和命令，不必新增镜像实现的测试。
- 改节点或图：跑 workflow 契约测试，覆盖跳过、汇合和恢复。
- 改插件：跑插件 HTTP 传输契约，确认 SDK 不隐式重试。
- 改权限或持久化：增加真实数据库场景，覆盖不同工作空间与重复请求。
- 改界面：检查类型、构建及浏览器实际操作，覆盖错误和空状态。

提交前运行与改动有关的检查；大改运行 `pnpm check`。不要通过放宽类型或吞异常来让检查变绿。

## 数据库迁移

在本地执行 `pnpm --filter @dramaflow/database migrate:dev` 前确保加载根 `.env`；可使用 Node 的 `--env-file` 或在已加载环境的终端执行。审查生成 SQL，迁移命名表达实际变更。已在其他环境应用的迁移不能回写，后续修复增加新迁移。

部署用 `pnpm db:migrate`，它只执行已提交迁移，不生成新 SQL。pgvector 扩展由初始迁移启用。

## 架构变更

在 docs 中记录具体问题、选项、最终决定和迁移影响。稳定约束写入 AGENTS.md，操作细节留在专题文档。不要把个人偏好或未经确认的路线图写成用户已经要求的事实。
